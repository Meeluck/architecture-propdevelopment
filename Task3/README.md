# Задание 3 Внешние интеграции

PropDevelopment хочет расширить бизнес-функции для собственников и жильцов. Компания планирует добавить в систему новые сервисы «Умный дом». Эти сервисы готов предоставить партнёр.

Вы согласовали техническое задание с бизнесом и выбрали две услуги для внедрения:

- Интеллектуальный домофон. Включает функции классического видеодомофона — открытие по звонку. Также есть возможность распознавать пользователей по биометрии (по лицу) и автоматически открывать дверь, если им разрешён доступ в дом.
- Интеллектуальный шлагбаум. Включает функции классического управления шлагбаумом и автоматически открывает доступ, если распознаёт номера автомобилей, которым въезд разрешён.

Новые сервисы должны быть доступны через текущее мобильное приложение, которое используют собственники.

## Что нужно сделать

1. Подготовьте диаграмму контекста в модели С4. Она должна отражать контекст, в котором будут работать новые бизнес-функции.
2. Доработайте диаграмму контейнеров PropDevelopment. Отразите на ней изменения, которые вы предлагаете сделать в ландшафте систем кампании в связи с внедрением новых бизнес-функций.
3. Сформируйте список требований, которым должны удовлетворить внешние интеграции. Для этого:
   1. опишите требования к безопасности,
   2. выделите протоколы аутентификации и авторизации,
   3. опишите, как будет организовано взаимодействие между системами предприятия и внешней платформой.

Когда выполните задание, загрузите в директорию Task3 диаграмму контекста, обновлённую диаграмму контейнеров и список требований.

## Решение

Диаграммы подготовлены в файлах:

- `context.puml` - контекстная диаграмма C4 для новых бизнес-функций;
- `container.puml` - доработанная контейнерная диаграмма для ландшафта PropDevelopment.

### Архитектурное решение

Новые функции добавляются в домен ЖКУ, потому что ими пользуются собственники через текущее мобильное приложение. В ландшафт PropDevelopment добавляется отдельный `smart-home-integration-app`. Он работает как фасад и anti-corruption layer между мобильным приложением, внутренними сервисами ЖКУ/CRM и платформой партнёра.

Партнёрская платформа остаётся владельцем физического управления домофоном и шлагбаумом, видеопотоков и алгоритмов распознавания лиц/номеров. PropDevelopment остаётся владельцем учётной записи собственника, связи собственника с домом/ЖК, согласий, правил доступа и аудита операций.

Мобильное приложение не обращается к устройствам напрямую. Оно вызывает `smart-home-integration-app`, а интеграционный сервис проверяет права собственника и передаёт партнёру только разрешённые команды или выдаёт краткоживущий токен на видеопоток.

### Требования к безопасности

1. Весь внешний трафик должен передаваться только по TLS 1.2+; для server-to-server интеграции с партнёром требуется mTLS и allowlist сетевых адресов партнёра.
2. Интеграция должна работать по принципу минимизации данных: партнёру передаются только данные, необходимые для конкретного сценария доступа. Массовая выгрузка собственников, квартир, автомобилей и истории операций не допускается.
3. Биометрические данные должны обрабатываться только при явном согласии собственника. PropDevelopment не хранит сырые фото, видеофрагменты и биометрические шаблоны; они обрабатываются на стороне партнёра по договору обработки данных. В PropDevelopment хранится только связь `ownerId` - `partnerSubjectId`, статус согласия и журнал операций.
4. Номера автомобилей относятся к персональным данным. Их нужно хранить в нормализованном виде с шифрованием на уровне БД или в виде хеша там, где полный номер не нужен. Передача номера партнёру допускается только для проверки конкретного события въезда.
5. Все команды открытия двери/шлагбаума должны проходить проверку прав: собственник должен быть привязан к соответствующему ЖК/дому/подъезду/парковке, услуга должна быть активна, а устройство должно относиться к этому объекту.
6. Для партнёра должны быть выделены отдельные технические клиенты, scopes и лимиты доступа. Доступ по умолчанию запрещён; партнёр не должен получать возможности читать или изменять данные других ЖК и управляющих компаний.

7. Все запросы партнёра к API PropDevelopment должны быть подписаны, содержать timestamp, correlationId и idempotency key. Повторные и просроченные запросы должны отклоняться.
8. События доступа должны журналироваться: кто инициировал действие, какое устройство использовалось, какое решение принято, какой был результат у партнёра. В логи нельзя писать сырое видео, биометрию, полные токены и секреты.
9. Должны быть настроены мониторинг, алерты и процесс реагирования на инциденты: ошибки API, всплеск отказов, подозрительное количество открытий, недоступность партнёра, ошибки распознавания.
10. При сбое распознавания автоматическое открытие не выполняется. Ручное открытие через приложение доступно только после успешной авторизации собственника и проверки прав.

### Аутентификация и авторизация

Для собственников используется OIDC Authorization Code Flow + PKCE в мобильном приложении. Пользовательский access token передаётся в `smart-home-integration-app`; сервис проверяет подпись токена, срок действия, аудиторию и scopes.

Для взаимодействия PropDevelopment с партнёром используется OAuth 2.0 Client Credentials + mTLS. Токены должны быть короткоживущими и ограниченными scopes, например:

- `smart-home.devices.read` - чтение статусов устройств;
- `smart-home.open.execute` - выполнение команд открытия;
- `smart-home.access.check` - запрос решения allow/deny по событию распознавания;
- `smart-home.events.write` - отправка событий устройств в PropDevelopment.

Для webhooks от партнёра дополнительно требуется подпись тела запроса или JWS, проверка timestamp и защита от replay-атак. Для видеопотока используются одноразовые краткоживущие media tokens, которые не дают доступа к API PropDevelopment.

### Взаимодействие систем

1. `smart-home-integration-app` получает из `tenant-core-app` и CRM минимальные данные для проверки прав: собственник, объект недвижимости, ЖК/дом/подъезд, активность услуги и доступные устройства.
2. Справочник устройств синхронизируется с партнёром: домофоны и шлагбаумы сопоставляются с ЖК, домами, подъездами и парковками в PropDevelopment.
3. При открытии двери или шлагбаума из приложения мобильная витрина вызывает `smart-home-integration-app`; сервис проверяет права, фиксирует попытку в журнале и отправляет команду в API партнёра.
4. При звонке в домофон партнёр отправляет событие в PropDevelopment. Мобильное приложение получает уведомление или событие по WebSocket, запрашивает краткоживущий токен и подключается к видеопотоку партнёра. Команда открытия всё равно проходит через `smart-home-integration-app`.
5. Для распознавания лица собственник сначала даёт согласие в приложении. После этого создаётся профиль у партнёра, а в PropDevelopment сохраняется только идентификатор профиля партнёра и статус согласия. При отзыве согласия интеграционный сервис отправляет партнёру команду удаления биометрического профиля.
6. При автоматическом открытии домофона партнёр распознаёт лицо и отправляет в `smart-home-integration-app` запрос проверки доступа с `deviceId`, `partnerSubjectId`, `eventId` и уровнем уверенности. PropDevelopment возвращает `allow` или `deny`; партнёр открывает дверь только при `allow`.
7. При автоматическом открытии шлагбаума партнёр распознаёт номер автомобиля и отправляет запрос проверки доступа. `smart-home-integration-app` сверяет номер с разрешёнными автомобилями для конкретного ЖК/парковки и возвращает `allow` или `deny`.
8. Все статусы устройств, результаты команд и события распознавания возвращаются партнёром через webhooks. Для повторяемых событий используется idempotency key, чтобы повторная доставка не приводила к повторному открытию.

Такое решение изолирует партнёрскую интеграцию в одном сервисе, закрывает проблему неконтролируемых API партнёров и позволяет расширять функции Умного дома без прямого доступа внешней платформы к внутренним CRM и данным ЖКУ.
